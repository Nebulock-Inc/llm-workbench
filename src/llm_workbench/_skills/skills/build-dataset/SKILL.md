# Build the test set

The test set is a **JSONL** file — one JSON object per line.

## The record contract

```json
{"id": "q1", "input": "What hunts cover LaunchAgent persistence?", "expected": "..."}
{"id": "q2", "input": "Summarize the last 24h of failed logins for acme-corp."}
```

- `input` — the standard field the default prompt template fills in.
- `expected` — ground truth used by checks like `exact_match` / `numeric_tolerance` (optional).
- `id` — a **stable** identity. Resume and analysis key on it; give every record one so runs
  line up across re-runs. If omitted, one is generated (and won't be stable if the text changes).
- Any other field is available to custom tasks and as an eval `{variable}`.

## Three ways to build it

**By hand** — fine for a pilot; write representative prompts that look like production traffic.

**From a spreadsheet** — every column becomes a field:
```bash
llm-workbench dataset from-csv prompts.csv -o test_set.jsonl --id-col qid
```

**Generated by an LLM** — a starter set to review and edit (not to trust blindly):
```bash
llm-workbench dataset generate --model anthropic/claude-sonnet-4-5 \
    --instructions "security-analyst questions about threat hunts and detections" \
    -n 30 --with-expected -o test_set.jsonl
```

## Sizing: pilot first, then the full N

- **Pilot:** ~10–20 representative records — enough to estimate how far apart the models are,
  not to settle the comparison. Run the pilot, then use the `power-analysis` skill to turn the
  observed effect into a target N.
- **Full set:** grow to the N that power analysis recommends. Because runs resume on `id`, you
  can append new records to the same dataset and re-run — already-scored pairs are skipped.

**Gate for the guide:** a JSONL file exists with stable `id`s and the fields the task and evals
reference; for the pilot stage, ~10–20 representative records.
